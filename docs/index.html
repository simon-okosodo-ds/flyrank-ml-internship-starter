Abstract. FlyRank's rule-based system for flagging declining content pages for editor review is only 40% precise in its top-50 recommendations, wasting 30 of every 50 weekly editor reviews on pages that were never a real priority. This paper asks whether a trained model, evaluated honestly on real production data, can beat that rule — and whether a page's reason for underperforming (genuine decay vs. a SERP-answered query vs. a fixable CTR problem) can be diagnosed alongside its rank. Using 9.8 million daily performance rows from FlyRank's pseudonymized internal warehouse (55 clients, 331,437 content items, Feb–Mar 2026), a Random Forest classifier was trained on prior-month signals to predict next-month improvement, validated with a client-grouped split to prevent memorization. An initial single-split result (Precision@50 = 0.820) was deliberately not trusted as final: 5-fold grouped cross-validation showed it sat within a wide 0.764 ± 0.135 range, and a first hyperparameter-tuning pass was found to leak across validation folds, inflating the score to an unvalidated 0.904. Nested cross-validation — tuning independently inside each fold — produced the honest, reportable result: Precision@50 = 0.892 ± 0.065, confirmed with a bootstrap 95% confidence interval of [0.240, 0.600] on the gap over baseline that excludes zero. This cuts wasted editor reviews from roughly 60% to 11% per week — about 25 extra productive reviews out of 50 — while a diagnosis layer classified 10.5% of eligible pages as likely SERP-answered, a pattern the existing rule cannot distinguish from genuine decline at all. This is decision-support evidence for FlyRank's editorial triage workflow, not a causal claim and not a claim about Google's ranking algorithm.

01 — Introduction / Problem

Editors can review 50 pages a week. The current rule wastes 30 of them.

FlyRank manages tens of thousands of pages across dozens of clients, but a human editor can carefully review only about 50 pages a week. The existing rule-based flag — in_striking_distance & has_real_volume — decides which 50 pages an editor opens first. On real March 2026 warehouse data, that rule is only 40% precise in its own top 50: 30 of 50 recommended pages turn out not to be real priorities. Every one of those 30 reviews is a paid editor-hour spent on a page that was never the problem, while a genuinely declining page elsewhere goes unlooked-at for another week.

A second, separate failure sits underneath the first: even when the rule is right that a page needs attention, it gives no reason why. A page whose clicks fell because Google now answers the query directly on the results page (no click opportunity left to recover) looks identical to the rule as a page that is genuinely stale and needs a rewrite — but the fix for each is completely different, and rewriting the first wastes the same editor-hour a second time.

The decision this project improves: which pages an editor opens first, and what kind of fix they should expect before opening the page — not just whether to review a page, but why.

February content-level features were joined to March outcomes on client_hash_id + content_hash_id. Pages needed real, measurable March volume (≥10 impressions) to compute a trustworthy outcome, and both months needed to match — leaving 130,969 eligible rows for modeling.

Deliberately excluded, and why:

  • trend_direction / trend_pct — these are the source of the existing rule's own label; using them as features would be circular.
  • Any FlyRank product-decision column (health_score, priority_score, action_type) — these encode a decision the current system already made; feeding them back in would just teach the model to copy that decision, not discover anything new.
  • GA4-derived engagement fields — only 4.2% of March rows have ga4_data_available IS TRUE, too sparse to trust as a feature this month.
  • Raw client names, domains, URLs, and search queries — never present in the release at all.

03 — Methodology

A forward-looking label, nested validation, and a diagnosis layer

Target

Unlike the starter pipeline's same-window is_declining_label, the label here is a genuine future outcome: did a page's CTR or average position improve from February to March? Features come entirely from February; the label comes entirely from March.

Features

impressions, clicks, avg_position, has_position_data, in_striking_distance, has_real_volume

All are knowable at the February decision point — no feature crosses into March. has_position_data was added after error analysis found avg_position = 0 (meaning "no position data," per the data dictionary — present in 303 of 130,969 rows) was being silently averaged in as if it were rank zero; the explicit flag resolved this without discarding the rows.

Baseline

The existing FlyRank-style rule, encoded transparently with no fitted weights: score = impressions × (in_striking_distance AND has_real_volume), where striking distance is position 11–30 and real volume is ≥100 impressions. Precision@50 = 0.400, re-evaluated on the real warehouse test population (the 0.240 figure quoted elsewhere in this internship comes from the separate 30,000-row starter CSV and is not interchangeable with this number).

Model

Logistic Regression, then Random Forest, matching the method ladder the starter pipeline itself used.

Validation design — the part that changed most

Grouped, not random. Every split groups by client_hash_id so no client's pages appear in both train and test — a naive random split (reported alongside, not hidden) lets the model memorize a client's template rather than learn a transferable pattern, and reached a suspicious 1.000.

A single split was not trusted as final. The original 70/30 client-grouped split scored 0.820. Re-run as 5-fold grouped cross-validation, the honest mean was 0.764 ± 0.135 — 0.820 sat within normal variation, but the spread was too wide to report a single number alone.

A hyperparameter search was caught leaking across folds. An initial tuning pass selected one "best" configuration using only the original 28 training clients, then reused those parameters across all 5 outer validation folds. Because some of those 28 clients inevitably landed in the test portion of later folds, the resulting 0.904 ± 0.086 was a second-order leak — the same class of problem, one level removed, as feeding a model a feature it shouldn't see.

Fixed with nested cross-validation. Hyperparameters were re-selected independently inside each outer fold, using only that fold's own training clients. The result barely moved — 0.892 ± 0.065 — confirming the improvement from tuning was real, not an artifact, while also being meaningfully more stable than the untuned model. A final model was then tuned once more and fit on all 40 eligible clients as the deployed artifact; its reported performance is this nested-CV estimate, since no held-out data remains once trained on everything.

Diagnosis layer

A four-category classifier reused from ML-03's diagnose() logic, remapped onto this notebook's Feb (prior) / March (last) structure:

Named up front: likely_serp_answered's real-world justification — that an AI Overview or featured snippet intercepted the click — rests on external industry reporting, not on FlyRank's own query-level SERP-feature data. It is a proxy signature, not a confirmed cause, and this paper never claims otherwise.

04 — Results

0.400 → 0.892 ± 0.065: a validated, leakage-checked lift

Precision@50 — baseline vs. final nested-CV model

Final model, mean Precision@50 across 5 grouped folds, each fold tuned independently (nested cross-validation) to rule out hyperparameter leakage: 0.892 ± 0.065. Base rate (share of pages that genuinely improved) was 45.2%.

The validation chain — from single split to the trusted number

Five numbers, one honest answer. The single-split result (0.820) and a leaked tuning result (0.904) were each rejected on their own evidence before arriving at the final, nested-cross-validated 0.892 ± 0.065 — reported here as the full chain, not just the ending, per this project's leakage-hunting discipline.

Diagnosis distribution — 130,969 eligible pages

1 in 10 eligible pages (13,775 of 130,969) show the "impressions held, clicks fell" signature — the exact pattern the old single-bucket "declining" rule cannot separate from genuine decay.

Why this baseline (0.400) differs from the 0.240 figure elsewhere in this internship

The starter pipeline's own reference result — quoted throughout the internship's lane guide — reports the rule-based baseline at Precision@50 = 0.240, but that number comes from the 30,000-row starter CSV, not the real warehouse. The 0.400 reported here is the same rule (in_striking_distance AND has_real_volume), re-evaluated directly on this notebook's actual 130,969-row warehouse test population. The two numbers describe different datasets and are not interchangeable; this paper uses the warehouse-computed 0.400 throughout.

Verbatim, from w05_model.ipynb — the baseline, re-evaluated on the same rows used for every model score in this paper:

baseline_score_test = X_te_g['impressions'] * (X_te_g['in_striking_distance'] & X_te_g['has_real_volume']) baseline_order = np.argsort(-baseline_score_test.values)[:50] baseline_p50 = y_te_g.iloc[baseline_order].mean() print(f"ML-07 baseline rule: Precision@50 = {baseline_p50:.3f}") >>> ML-07 baseline rule: Precision@50 = 0.400

Statistical confirmation

A bootstrap (1,000 resamples) of the gap between model and baseline Precision@50 on the held-out test set gives a mean gap of 0.433, with a 95% confidence interval of [0.240, 0.600] — this does not include zero, so the model's advantage over the baseline is a statistically supported claim on this test population, not just two point numbers placed side by side.

05 — Limitations & honest framing

What this work cannot claim

  • Snapshot, not causal proof. This shows an observed association between February signals and March outcomes. It does not show that acting on a recommendation causes a page to improve — that needs an A/B test or another causal design this data alone cannot provide.
  • Precision@50 varies across client-grouped folds (0.764 ± 0.135, pre-tuning). A single split showed 0.820, which is within normal range but was deliberately not reported as the primary result. A 10-fold re-check (0.710 ± 0.123) produced a meaningfully different mean than the 5-fold check — the honest representation of model performance is a validated range, not one decimal.
  • An earlier fold-variance hypothesis was corrected after direct investigation. A thin correlation (computed from only 5 folds) initially suggested larger clients perform worse. Pulling the actual data for the worst-performing fold's two clients showed this was wrong: one small, low-traffic client with an atypically low improvement rate (0.264 vs. 0.452 dataset average) was the real cause, not client size — the large client in the same fold performed almost exactly at the dataset average (0.456).
  • A first hyperparameter-tuning pass leaked across folds and was rejected. Reusing one "best" configuration (selected using only 28 training clients) across all 5 outer validation folds produced an inflated, unvalidated 0.904 ± 0.086. Nested cross-validation — tuning independently inside each fold — gave the honest 0.892 ± 0.065 used throughout this paper.
  • avg_position = 0 bug, found via error review and partially addressed. Per the data dictionary, 0 means "no position data," not literal rank zero. An explicit has_position_data flag was added so these 303 rows are no longer silently averaged in as rank zero. This improved model stability (std narrowed from 0.135 to 0.119) but not raw accuracy — reported honestly as a partial, not complete, fix.
  • A simplified 3-feature model was tested and rejected. Dropping two engineered flags won on a single split (0.860) but underperformed the full feature set once properly validated across 5 folds (0.724 ± 0.137 vs. 0.764 ± 0.135) — a reminder that a single-split win does not guarantee a validated one.
  • Only 40 of 55 March clients appear in the final model (28 train + 12 test in the original split). Investigated directly: only 5 are explained by having zero February history at all; the remaining 10 were removed by the ≥10-impression March volume filter — a deliberate, named filtering choice, not a join bug.
  • GA4 engagement signal is unusable this month. Only 4.2% of March rows have ga4_data_available IS TRUE — far too sparse to trust as a feature without an explicit "not available" category.
  • The SERP-answered diagnosis is directional, not confirmed. No query-level SERP-feature data (whether an AI Overview fired) exists in this release — the pattern is a proxy signature backed by external industry reporting, never presented as proof.
  • The ≥10-impression March filter excludes pages that went fully silent. A page could "improve" by disappearing entirely from a declining trend into total silence — that would not register as improved here.

06 — Ranked recommendations

The action playbook

Every recommendation below carries a reason code so an editor can see why, not just that.

DiagnosisRecommended actionHuman-review requirement
genuine_declineRefresh or rewriteConfirm this isn't consolidation, seasonality, or noise before commissioning a rewrite
likely_serp_answeredFlag for review only — no rewriteNever auto-confirmed as SERP-cannibalized; treat as "needs human judgment," not a settled diagnosis
ctr_fixableReview title / meta descriptionConfirm avg_position ≠ 0 (no-data) before trusting the position signal
stable_or_improvingNo action — protect, don't touch—

What should never be automated

  1. Auto-publishing a rewrite from genuine_decline alone — a human must rule out consolidation, seasonality, and noise first.
  2. Auto-confirming likely_serp_answered as cannibalization — the evidence is external and directional, not FlyRank's own confirmed signal.
  3. Treating model_score as a guaranteed outcome — it is a validated, honest probability (Precision@50 = 0.892 ± 0.065, nested cross-validation), not a promise.

Monitoring / retrain triggers

  • Re-run monthly at minimum — this is a fixed Feb→Mar snapshot and will report the same pages forever without a refresh.
  • Watch the diagnosis-share baseline (CTR-fixable 58.1% / stable 23.9% / SERP-answered 10.5% / decline 7.5%) — a sharp shift signals something platform-wide changed.
  • Retrain if Precision@50 on a fresh month, re-validated with the same nested-CV procedure, drops meaningfully below ~0.89.
